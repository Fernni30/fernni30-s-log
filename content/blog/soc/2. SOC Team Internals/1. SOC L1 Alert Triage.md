## 1. 📋 SOC 알림(Alert) 개요 정리

### ㄱ. 🔔 이벤트 → 알림 생성 흐름

```
이벤트 발생 → 시스템이 로그 기록 → SIEM/EDR으로 로그 수집 → 의심 이벤트에 알림 생성
```

- **이벤트(Event)**: 사용자 로그인, 프로세스 실행, 파일 다운로드 등
- **알림(Alert)**: 보안 솔루션이 특정 이벤트 또는 이벤트 패턴을 감지했을 때 자동 생성하는 알림
- SOC 팀은 하루 수백만 건의 로그를 받지만, 알림 덕분에 하루 수십 건만 검토하면 됨

---

### ㄴ. 🛠️ 알림 관리 플랫폼 종류

| 솔루션        | 대표 예시                | 설명                                          |
| ------------- | ------------------------ | --------------------------------------------- |
| **SIEM**      | Splunk ES, Elastic       | 대부분의 SOC팀에 적합한 강력한 알림 관리      |
| **EDR / NDR** | MS Defender, CrowdStrike | 자체 대시보드 있으나 SIEM/SOAR 사용 권장      |
| **SOAR**      | Splunk SOAR, Cortex SOAR | 대규모 SOC에서 여러 솔루션의 알림을 통합 관리 |
| **ITSM**      | Jira, TheHive            | 티켓 기반 맞춤형 관리 시스템                  |

---

### ㄷ. 👥 SOC 팀별 역할

| 역할              | 주요 업무                                          |
| ----------------- | -------------------------------------------------- |
| **L1 애널리스트** | 알림 1차 검토 → 위협 여부 판단 → L2에 에스컬레이션 |
| **L2 애널리스트** | L1이 올린 알림 심층 분석 및 대응(remediation)      |
| **SOC 엔지니어**  | 알림에 충분한 정보가 담기도록 시스템 유지          |
| **SOC 매니저**    | 트리아지 속도·품질 추적 및 관리                    |

## 2. 알람 속성 정리

| 속성                         | 설명                                                            | 예시                                                          |
| ---------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------- |
| **Alert Time** (알림 시각)   | 알림 생성 시각. 실제 이벤트보다 보통 몇 분 후에 생성됨          | 이벤트: 15:32 → 알림: 15:35                                   |
| **Alert Name** (알림 이름)   | 탐지 룰 이름 기반으로 무슨 일이 일어났는지 요약                 | Unusual Login Location, Windows RDP Bruteforce                |
| **Alert Severity** (심각도)  | 알림의 긴급도. 탐지 엔지니어가 초기 설정, 분석가가 수정 가능    | 🟢 Low → 🟡 Medium → 🟠 High → 🔴 Critical                    |
| **Alert Status** (상태)      | 현재 누군가 작업 중인지, 완료됐는지 나타냄                      | 🆕 New → 🔄 In Progress → ✅ Closed                           |
| **Alert Verdict** (판정)     | 실제 위협인지 오탐인지 분류                                     | 🔴 True Positive (실제 위협) / 🟢 False Positive (오탐)       |
| **Alert Assignee** (담당자)  | 알림을 검토하도록 배정된 분석가. 담당자는 해당 알림에 책임을 짐 | 담당자 = Alert Owner라고도 불림                               |
| **Alert Description** (설명) | 알림의 맥락 설명. 보통 세 파트로 구성                           | ① 탐지 룰 로직 ② 왜 이게 공격 징후인지 ③ (선택) 트리아지 방법 |
| **Alert Fields** (상세 필드) | 알림을 트리거한 실제 값들. 분석가 코멘트 포함                   | 영향받은 호스트명, 입력된 커맨드라인 등                       |

## 3. 알림 우선순위 지정

> 알림이 많을 때 **어떤 알림을 먼저 처리할지** 결정하는 프로세스. 실제 위협을 제때 탐지하기 위해 매우 중요하며, 보통 SIEM/EDR에서 자동 정렬 로직으로 구현됨.

### ㄱ. 📌 한눈에 보는 우선순위 로직

```
① New 알림만 필터링
        ↓
② Severity 높은 것 먼저 (Critical > High > Medium > Low)
        ↓
③ 같은 Severity면 오래된 것 먼저 (Oldest → Newest)
```

## 4. 문제 풀이

> 문제 풀이 방식

- 해당 알림의 Description을 보고 해당 문제가 실제 공격인지 오탐인지 판별하여 SIEM에서 본인이 직접 처리
  - 본인: Assignee = You(L1)을 의미
  - 처리: Closed

- 원래 실무에서는 규칙에 따라 보고서를 작성,
  - 회사 규칙에 따라 L2에게 Assignee,
  - Verdict를 In progress 설정을 넘기는 것도 있음
